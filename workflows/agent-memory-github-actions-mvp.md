# Agent Memory 定时研究任务 MVP 设计

- 版本：0.3；修订日期：2026-10-19。
- 状态：**仅设计，尚未实现或启用**。本文中的频率、路径与参数是后续实施约定。
- 实施进度：已有[离线骨架](offline-research.md)与[真实来源采集测试](real-source-collection.md)，所有分析/审阅仍为模拟，结果只进测试区；真实模型、会员授权、GitHub 自动入库及定时任务仍未实现或启用。
- 目标：GitHub Actions 定时发现 Agent Memory 资料，生成带证据的研究记录，经独立审阅模型与规则校验通过后自动入库。
- 总体架构见[三 Agent 总体架构](three-agent-architecture.md)。沿用[主题配置](../config/research_topics.yaml)、[Schema v1](source-schema.md)、[维护规范](maintenance.md)和现有模板，保持 Markdown + YAML。

## 1. 范围与成功标准

闭环为：**定时触发 → 发现与查重 → 固定原文证据 → 研究模型生成 → 独立模型审阅 → 规则校验 → PR 自动合并 → Obsidian 拉取**。

本版只设计 Research Agent 的首个来源研究任务：处理启用的 `agent-memory`，产出新来源笔记、已有来源的独立更新材料和批次回执。`agent-rl` 继续停用。综合研究报告、Insight Agent、Writing Agent 属于总体架构的后续阶段，本任务不自动生成洞察或文章，不连接公众号发布接口。

**正常入库流程不要求人工审阅或人工点击合并。** 内容须有可核实的原始来源、稳定身份、明确阅读范围、可定位的证据，并同时通过独立模型审阅和确定性检查。运行成功、模型通过、PR 创建和合并成功分别记录；只有通过的最终产物进入 `main` 并登记为 `accepted`，才算正式入库。研究消费者仅读取这些产物，不把检查点草稿或失败记录当成研究结论。

没有合适的新资料也是合法结果，需要保存完整扫描回执。规则或权限阻碍自动合并时显式报错，不能把“模型说通过”当作已经入库。

启用前对现有人工入库资料做只读盘点，在独立基线清单登记 `human_baseline`、路径和散列，允许后续研究使用，不修改旧文件或补造模型审阅。后续人工新增/修改按只读校验更新基线登记。自动新产物必须满足 `accepted` 与审阅条件；身份查重始终覆盖全库。

## 2. 触发频率与运行上限

| 项目 | MVP 决策 |
| --- | --- |
| 主入口 | **每周二、周五北京时间 09:00**，每周两次。拟用 UTC cron 为 `0 1 * * 2,5`，对应 `Asia/Shanghai`；只记录设计，不创建实际配置。 |
| 执行环境 | 采集/发布拟在 GitHub 托管 Ubuntu runner 读取 `main`；会员分析优先评估符合资格的本地/自托管执行器，与采集解耦。临时 runner 的会员调用资格及分析主机可用性仍待验收，不假设本地在线或所有阶段已能在 Actions 完成。 |
| 辅助入口 | 后续提供 `workflow_dispatch`，仅用于验收、恢复批次和指定区间补跑；共用查重、审阅、预算与写入保护。 |
| 扫描时间窗 | 首次最近 7 天；随后从各来源最后已合并的完整扫描游标向前重叠 48 小时，扫描到本批固定截止时间。周二覆盖上次周五以来，周五覆盖上次周二以来，不能只查运行当天。 |
| 发现上限 | 每个来源每批最多检查 50 条候选元数据，超额保存续扫线索；不能标记为已完整扫描。 |
| 研究上限 | 每批最多 3 份，优先 2 篇论文 + 1 篇博客，不足可互补；同一博客发布方最多 1 篇。更新材料也占名额。 |
| 时间上限 | 每次执行最多 30 分钟，中断后读取远端清单恢复同一批次。 |
| 模型上限 | 每份最多 4 次请求尝试：研究模型最多 2 次、审阅模型最多 2 次；每批累计最多 12 次。通常为研究 + 审阅，需要时再修订 + 复审一次。网络和恢复重试也占相应槽位，补跑不重置。 |
| 输入输出 | 模拟账本检查输入 16,000、输出 2,000 token 上限；会员后端预览不支持 `max_output_tokens`，真实输入/输出、时间与额度限制需另行验收，不能把模拟参数当服务端硬限制。超限须明确节选范围。 |
| 并发上限 | 同时最多 1 个活动批次、1 个入库 PR。内容失败不阻塞其他合格项；配置或合并故障未解决时停止新增付费研究，优先恢复发布。 |

实施前明确 `research_model_id` 和 `review_model_id`，**两者必须是不同的具体模型 ID**，使用独立上下文；不能只换提示词或把同一模型重命名为审阅者。缺失审阅配置时不能退回研究模型自审。具体模型、版本、批次/月度调用与会员用量边界在实施阶段确定；普通 API 费用只在另获授权选择该后端时适用，当前不添加凭据或调用模型。

研究、修订、审阅、复审和失败重试都计入调用及用量预算。请求前持久化调用预留，关闭隐式重试；结果未知不能返还预留。会员真实额度不可观测时标记未知，不将模拟单位换算成真实费用；具体用量门禁按会员后端验收。若以后另行采用付费 API，需另外预留最大费用。额度不足时留下待办，不能新建批次绕过限制或自动切换付费后端。

GitHub 的定时任务可能延迟或丢失，09:00 是计划时间；本设计保留用户指定的整点，不另行调整时间。恢复完整性依靠游标和清单。参见 [GitHub schedule 文档](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)。

## 3. 资料来源与筛选

首版使用三个一手来源，关键词取自主题配置，同时判断是否涉及 Agent 记忆机制。GPU 内存容量等仅词面相关内容不入选。

| 来源 | 发现方式 | 原文核实 |
| --- | --- | --- |
| arXiv | [官方 API](https://export.arxiv.org/api/query)，组合 Agent 与记忆关键词，按 `lastUpdatedDate` 降序分页；初期重点 cs.AI、cs.CL、cs.MA，验收时检查漏检与噪声。 | 固定官方 HTML/PDF 的实际 `vN`，保留基础编号、首次发布及更新时间；旧论文新版也需发现。 |
| Letta | [官方博客列表](https://www.letta.com/blog/)，筛选 memory、context management、Agent 长期状态等内容。 | 区分产品设计、工程经验与实验结果，保留原文署名和日期。 |
| LangChain | [官方博客列表](https://www.langchain.com/blog)，筛选 long-term memory、context engineering 等内容。 | 区分框架能力、实现建议与有证据的效果，核实真实署名和日期。 |

截至 2026-10-18 的来源核对，LangChain 旧 `blog.langchain.com/rss/` 跳转后返回 HTML，不能当作已验证 RSS；Letta 首版同样使用列表页。格式、内容类型或跳转域名异常应报告来源失败，不等于零新增。

arXiv 的 `published` 是首次版本日期，`updated` 是当前版本更新时间；按更新排序并在本地检查时间窗，不能只查首次提交日期。连续 API 请求至少间隔 3 秒，参见 [arXiv API 手册](https://info.arxiv.org/help/api/user-manual.html)。博客列表不一定显示旧文修订，因此每次周二/周五运行另轮查最多 5 个已入库博客 URL，按上次核查时间轮转；这不能保证发现所有历史更新。

按主题相关性、新机制或评测证据、对现有资料的补充程度排序，同分优先较早积压项。记录无关、重复、待核实、额度延后和审阅拒绝的理由。额度延后项保留，不能随扫描游标推进而丢失。厂商博客可提供工程视角，不能单独证明行业趋势。

## 4. 研究、独立审阅与修订

采用轻量 Python 流程控制抓取、身份、预算、调用和写入。模型只读材料、返回结构化结果，不直接操作 Git。未来默认评估官方 **Sign in with ChatGPT** 会员授权后端，而非普通 API Key 计费路径；适用资格、可用的两个不同模型、参数限制和执行主机按[会员分析设计](chatgpt-analysis-handoff.md)单独验收。本轮只生成交接包和模拟响应，不登录、不读取既有 Codex/浏览器凭据，不自动退回付费 API。

1. **规划**：检索全库和未完成批次，规范化身份；新来源先持久化预留 UUID v4、固定时间窗和基线 commit，再开始模型调用。
2. **获取证据**：通过受信任的抓取步骤取得白名单原文，优先 HTML，其次可直接提取的 PDF 文本；不增加 OCR、浏览器自动化或付费墙绕过。
3. **研究生成**：向研究模型提供固定版本原文证据和研究问题，产出摘要、方法/主张、证据定位、局限、主题关系和明确标识的推断。元数据由已核实原文确定，未知作者为 `[]`、未知发布时间为 `null`。
4. **独立审阅**：先做候选格式、身份及证据完整性的确定性检查，再由新上下文的审阅模型读取候选、原始证据包、元数据及相关既有资料，不依赖研究模型重述代替原文。逐项核对身份、日期、版本、引文、关键主张、实验适用范围、遗漏局限和事实/推断边界。
5. **有限修订**：`revise` 返回具体问题，研究模型至多修订一次，审阅模型重新完整审阅。只有最后一版 `pass` 才能提交；不能把上一版通过结论套到新稿。请求重试占用同一角色额度，耗尽则延期。
6. **确定性检查与入库**：程序验证格式、身份、引用路径、摘录是否出自证据、散列、预算和写入白名单。全部通过后，将确切产物提交到入库分支，自动 PR 合并；任何硬性检查失败都不能由模型批准豁免。

每个证据包记录原文 URL、抓取时间（UTC）、版本、规范化文本散列、章节/页码/段落、必要短摘录及 `full_text` / `excerpt` / `abstract_only` 覆盖范围。只有摘要时，可通过的是明确标注的摘要级研究线索，不能输出声称来自全文的实验结论。HTTP `Last-Modified`、正文散列变化只是更新线索，不冒充作者修订日期。不把整份 PDF、网页镜像或完整请求写入仓库。

审阅结果使用独立运行记录，不向现有来源 Frontmatter 添加字段：

| 内容 | 必须记录或满足 |
| --- | --- |
| 决策 | `pass`、`revise`、`reject`、`blocked` 之一；不是用单一主观评分决定入库。 |
| 核查与问题 | 关键主张及其证据 ID、支持/不支持/不确定判断；问题的位置、严重程度、理由和修订建议。缺失、格式错误或仍有阻塞问题的“pass”无效。 |
| 身份与版本 | 配置的具体研究/审阅模型 ID、实际响应身份、请求/响应标识、提示词版本、覆盖范围与原文版本；返回身份不能确认配置要求时停止。 |
| 绑定对象 | 候选正文与元数据散列、证据包散列、参考的 `main` 基线 commit；这些值由程序计算并验证，不能信任模型自行填写的散列。 |
| 决策效力 | `pass` 仅是对该版本的质量判断，不等于事实绝对正确。候选、证据或基线变化后原审阅失效，重新检查并审阅。 |

`reject` 对当前候选终结，不自动反复提交；原文出现新版本或有新的核实证据时才能重新规划，沿用来源身份并保留历史理由。`blocked` 表示缺失原文、身份未解、审阅服务故障等，记录可恢复条件后进入待办。暂时失败项不进入正式来源目录，不要求人工批准其他正常项。

修订一次后仍未通过，则终结当前分析轮次；跨批交接保留修订次数和终结原因，同一证据版本不能作为普通失败换批重置。只有新证据、原文版本或已满足的明确恢复条件出现后才重新规划。

原文中的命令或提示均为待研究文本。两个模型都不接触授权凭据、shell 或仓库写入工具；未来官方授权所得应用凭据只由受信任分析客户端安全保存和读取，不进入仓库、提示词、资料、日志或 PR。本轮不实现认证。

## 5. 去重、更新与人工内容保护

比较[维护规范](maintenance.md)中的每个已知身份键：arXiv 基础编号、规范化 DOI、保守规范化 canonical URL。查重覆盖 **`main` 全库、活动检查点/入库 PR、当前批次、过去的拒绝/待办记录及人工处理决定**。

| 情况 | 自动处理边界 |
| --- | --- |
| 新身份且审阅通过 | 按现有模板创建稳定 ID 的新笔记，初始化 `status: inbox`；正文标记“AI 研究记录，已通过独立模型审阅”，链接审阅回执。 |
| 同身份、同版本且无实质变化 | 跳过研究，不刷新旧笔记日期、状态或关联。 |
| 论文新版或已知博客正文变化 | 只生成通过审阅的独立更新材料，记录原 ID、新旧版本/散列及影响；原来源文件保持不变。 |
| 身份键冲突或只有标题相似 | 记录 `blocked_identity`，不猜测合并，也不建立可能重复的正式记录；有可靠原始证据后重新核实。 |
| arXiv 与期刊版本可能相同 | 仅在原始元数据或原文明示对应关系时共享身份；arXiv abs/pdf/各 vN 归同一基础编号。 |
| 博客解读论文 | 各自保留身份；新记录只引用已经存在且核实的关联，不回写旧记录。 |

`published_at` 是首次发布日期，`collected_at` 是首次录入日期，`updated_at` 是本库笔记修改日期；原文更新时间写入正文或清单。自动审阅结果、运行状态和人工阅读状态分开，**模型通过不会自动把资料设为 `analyzed`**，现有 Schema 的人工状态约定继续有效。

所有已有正文、批注、状态、主题、关联及人工修改过的机器人产物均受保护。新笔记的人工笔记章节留空；自动化只创建新文件。旧笔记的修改继续按维护规范逐段进行，不是自动入库的前置审批步骤。以后若需要自动维护指定段落，须另立明确所有权规则，不由本设计推定权限。

## 6. 检查点与正式入库的写入边界

首版采用两个用途明确的 Git 分支，不引入数据库：

- `codex/agent-memory-state-<batch-id>`：持久检查点，保存计划、不可变 attempt、候选版本和审阅结果；不作为知识输入，不合并未通过正文到 `main`。既有检查点也不可覆盖，补跑追加新文件。
- `codex/agent-memory-<batch-id>`：从当前 `main` 建立的干净入库分支，只包含最终通过的产物及必要运行回执，同批最多一个 PR。检查点分支失败时不开始付费调用；没有持久结果就不能声称可恢复。

| 正式入库路径 | 规则 |
| --- | --- |
| `sources/papers/<primary-topic>/<paper-id>.md`、`sources/blogs/<primary-topic>/<blog-id>.md` | 按主要研究方向只创建预留 ID 的通过产物；多主题不复制，已有路径绝不覆盖。 |
| `reports/research-runs/<batch-id>/manifest.yaml`、`attempt-<n>.yaml` | 创建批次与执行回执，记录时间窗、候选身份/预留 ID、各来源完整性、用量、决定、待办和结果散列；不携带未通过候选的完整正文。 |
| 同批次下的 `reviews/<source-id>-r<n>.yaml` | 保存通过产物的结构化审阅记录；失败项保留理由和检查点引用，不能冒充已接受研究。 |
| 同批次下的 `summary.md`、`updates/<existing-source-id>.md` | 确定性计数回执及通过审阅的独立更新材料；后续补充使用新 attempt 编号路径。 |

检查点使用上述批次目录下的 `candidates/` 和运行记录保存未通过版本，不能混入正式入库分支。知识消费者依据 `main` 中已登记 `accepted` 的产物路径/散列读取，不遍历检查点或把回执计数当成综合研究报告。

自动化无权改模板、Schema、主题配置、已有笔记、既有研究报告、洞察、文章及 `.obsidian/`。检查点和 PR 分支发现人工编辑、同名路径或非本任务提交时，保留内容并阻止自动覆盖。按预期远端 head 推送，不强推、不自动解决笔记冲突；分支被占用时换新命名的发布分支需记录关联，并重新审阅合并候选，不能删除原分支来恢复。

`batch-id` 使用固定逻辑时间槽，如 `agent-memory-20261020T010000Z`（周二北京时间 09:00），`attempt` 递增并关联 GitHub run ID。补跑沿用批次时间窗、来源身份和预留 UUID；不得重新生成 ID 或重置额度。

## 7. 状态、游标与失败补跑

- **批次**：`planned → researching → reviewing → ready_to_merge → merged`，另有 `partial`、`failed`、`blocked_configuration`。模型通过与 GitHub 合并成功分开。
- **资料**：`discovered → queued → generated → reviewed_pass → validated → proposed → accepted`；审阅要求修改时仅允许一次 `revising → reviewing`，另有 `rejected`、`blocked`、`deferred`。`accepted` 由合并确认推导，不能在合并前写成已完成。
- **游标**：各来源独立记录。完整扫描区间及待办回执真正合并后才能推进；失败来源或分页未完成不推进。深读额度未覆盖的候选留在持久队列，不随发现游标丢失。

检查点先保存规划与费用预留，再调用研究/审阅模型；每份完成后持久化结果，未变的通过产物可复用。候选、证据或 `main` 基线改变时审阅失效，预算允许则重新审阅；额度不足则延期。模型完成到持久化之间仍可能重复付费，未知结果保守计费，不宣称恰好一次。

基线变化的失效规则只针对待发布候选；历史 `accepted` 产物不会因主分支无关更新而被整体撤销，后续证据变化通过独立更新材料处理。

| 情况 | 恢复策略 |
| --- | --- |
| 抓取超时、429、5xx | 最多重试 2 次，指数退避并遵守 `Retry-After`；403/认证失败不反复重试。模型重试同时受每角色 2 次、每份 4 次和每批 12 次约束。 |
| 列表解析失败、分页超过上限 | 标记来源失败/未扫完，记录续扫信息；恢复时重叠扫描并去重，不将变化列表的固定页码当作稳定快照。 |
| 审阅 `revise` 后仍未通过 | 停止该候选，记录问题；其他通过项继续入库。`reject` 不盲目补跑，`blocked` 按缺失条件恢复。 |
| 审阅模型不可用或输出不合格 | 有额度才重试；否则延期，不能跳过审阅或交给研究模型自批。 |
| 运行超时、取消或调用结果未确认 | 从检查点恢复同一批次，复用已持久化内容和 ID，保守核算已预留用量。 |
| 内容部分失败 | 只将通过项和运行回执自动合并；失败/额度延后项转入后续合法时间槽的新批次，沿用来源 ID、历史决定和月度用量。 |
| 漏跑或延迟多次 | 从最后已合并游标补扫，达到上限分批继续，不能跳过未覆盖区间。 |
| PR 创建失败或合并结果未知 | 先查相同批次 PR、远端文件散列和合并状态；已合并则确认，不重复发布；未合并则只恢复发布，不重新研究。 |
| PR 因规则、权限、必需检查而不可自动合并 | `blocked_configuration`，保存通过产物与错误，暂停新增付费研究；不改权限、不绕过规则，也不把日常流程退回人工审批。 |
| PR 被人工关闭或分支被修改 | 保留现场和已消费预算，记录 `blocked_external_change`，不自动重开以对抗该操作；无冲突的其他资料可在后续重新规划。 |

无新资料且扫描完整时，通过规则校验的扫描回执可单独 PR 自动合并；它不包含研究结论，不需要调用模型“批准零结果”。只有审阅拒绝项的批次也可合并经过校验的处理决定/用量回执，不能混入未通过正文。全来源抓取失败则运行失败并保留检查点，不推进扫描游标。

定时、补跑、检查点写入和发布采用同一 concurrency 组，`cancel-in-progress: false`；待运行队列不承担持久补跑职责，参见 [GitHub concurrency 文档](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)。Summary 显示来源覆盖、各决策数量、用量、待办、合并状态和最近完整扫描。首版只使用 GitHub 运行状态/PR，不增加外部消息渠道。

## 8. PR 自动入库、权限与审计

1. 读取受信任的 `main` 代码和配置，检查并恢复活动批次；fork PR 或原文中的指令不能触发带密钥的研究。
2. 按执行职责隔离权限：会员分析执行器只读指定证据，不持 Git 写权限；凭据按官方授权方案保存在符合资格的分析主机，不默认注入 GitHub-hosted runner。GitHub 采集校验 job 仅 `contents: read`；保存检查点/发布 job 取得必要 `contents: write`，不持会员凭据；PR job 另需 `pull-requests: write`。合并 job 使用 `contents: write` 及所需的 PR/checks/statuses 只读权限。GitHub 权限须按 **job** 隔离，不能靠同一 job 的 step 降级，参见[官方权限说明](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token#modifying-the-permissions-for-the-github_token)。写入路径再由程序白名单限制。
3. 从检查点选取最终通过项，在当前 `main` 基线上组装干净提交并创建可合并的机器人 PR。PR 正文记录模型决定、证据范围、版本、失败项、费用和检查结果；正常流程不创建等待人工放行的 Draft PR。
4. 合并门禁核对最终文件散列、审阅记录、PR head SHA、base/main SHA、校验结果和仓库现有规则，全部满足才自动请求合并。审阅报告存入提交时只绑定内容/证据/基线散列，最终 head 与审阅记录的映射留在 Actions/PR 审计中，避免在提交内自引用“本提交 SHA”。
5. 内容、证据或 `main` 基线变化使模型审阅失效，必须重新校验/审阅。PR head 变化使合并门禁失效，须重验差异；只有能证明仅追加确定性审计文件、候选/证据/基线均未变时，才可复用模型回执并重新绑定最终 head，避免审阅报告提交造成自引用循环。调用合并 API 时必须传已验证的 head `sha`，收到 409 则停止并重新核查；它只能锁定 head，不能锁定 base，不能把“合并前再读一次 main”宣称为无竞态保证，参见 [GitHub merge API](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request)。
6. 启用前验证现有 strict required checks 或 merge queue 能检查最新合并结果，并能在无人值守条件下实际完成。仓库若缺少可保证该门禁的配置、要求人类审批、或执行器不支持已有队列规则，记为 `blocked_configuration`；后续配置另行明确处理，本轮不改规则或绕过审批。
7. 合并后读取 `main` 确认产物散列和已合并 PR，才登记 accepted 与有效游标。合并确认是对 Git 状态的推导，后续回执记录，不预先伪造状态；Obsidian 继续使用现有 Git 同步拉取。

模型审阅记录不是 GitHub 用户的 approving review，不能替代仓库强制的人类审批。`GITHUB_TOKEN` 也有后续工作流触发规则；部分机器人 PR 事件可能创建等待用户批准的运行，参见 [GITHUB_TOKEN 文档](https://docs.github.com/en/actions/concepts/security/github_token)。定时或手动任务中的校验通过不一定满足 PR 的 required checks，参见[必需状态检查说明](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks#checks-from-some-workflow-jobs-are-not-evaluated)。若因此无法完成无人值守检查，就明确阻塞，不能静默使用个人 token、降低规则或假装完成入库。

此处定义的是后续实施的权限和合并验收条件，不表示已经检查或更改当前仓库的保护设置。Obsidian 本地配置保持原样；本地编辑与云端更新冲突时保留两侧内容，不自动覆盖或强推。

## 9. 后续实施与启用门槛

当前已实现离线骨架、真实来源采集测试与隔离目录；不创建凭据、实际 GitHub workflow 或定时任务，不调用真实模型，不改正式研究资料，不发布公众号。测试状态为 `test_accepted`，不代表本文定义的 `accepted`，也不模拟已在 GitHub 合并。

后续实施预计增加来源/任务 YAML、轻量执行脚本和 GitHub workflow；先不含 schedule，完成固定样例演练，再经授权进行有限额度的真实手动验收。需要固定两个模型、预算和依赖，验证不同模型身份、独立证据审阅、失败闭环以及自动 PR 合并的规则兼容性。

验收通过且另获启用授权后，才添加周二/周五 09:00 的 schedule。基础设施首次验收与启用可由项目所有者决定，日常研究入库不设置人工内容审阅门槛。

| 验收场景 | 必须观察到的结果 |
| --- | --- |
| 周二/周五运行，或中间漏跑 | 对应北京时间 09:00，固定窗口覆盖上个有效游标以来的资料，重叠去重，不只查当天。 |
| 新论文/博客通过 | 两个不同模型独立生成/审阅，证据可定位，规则通过后 PR 自动合并；新来源 `status: inbox`，accepted 可追溯。 |
| 同模型冒充审阅、模型未配置、审阅超时 | 不自审、不默认通过；无未经审阅的研究正文进入 main。 |
| revise、reject、格式错误或假 pass | 修订最多一次且重审；阻塞问题不能放行，合格项仍可独立入库。 |
| 同批、后续批次或 PR 中同一来源 | 不重复建档或更换 ID；arXiv abs/pdf/vN 命中同一研究，新版仅产出独立更新材料。 |
| 摘要级证据、摘录不匹配、主张过度推广 | 标注阅读范围或阻止对应结论；不能伪装全文分析或用评分替代证据。 |
| 人工编辑已有笔记、检查点或 PR | 原内容保全，不重置人工状态/关联，不覆盖冲突。 |
| 基线、候选、证据或 PR head 变化 | 旧审阅/检查失效，重新核对并执行有效门禁；无预算则延期。 |
| 费用耗尽、429、超时后补跑 | 研究与审阅重试都计数，未知费用保守扣减，预留 ID 不变，补跑不重置额度。 |
| 部分来源失败、单份审阅失败 | 完整游标按来源推进，失败待办保留，不阻塞其他合格产物。 |
| PR 已合并但响应丢失，或被外部关闭 | 查询实际状态后处理，无重复 PR/重复研究，不对抗人工关闭。 |
| GitHub 要求人类审批、检查待批或规则不兼容 | 显式 blocked_configuration，不自动绕过；不会宣称无人值守已完成。 |
| 离线阶段交付 | 运行骨架仅写隔离测试结果，不改正式研究资料，不创建实际 GitHub workflow、Secret 或公众号发布。 |

## 10. 当前设计的可复现检查

在仓库根目录执行（依赖见 `workflows/requirements.txt`）：

```sh
python3 workflows/validate.py
git diff --check
git diff -- workflows/README.md workflows/three-agent-architecture.md workflows/agent-memory-github-actions-mvp.md
git status --short
git ls-files '.github/workflows/*'
```

最后一项本轮预期无输出；未跟踪文件同时通过 `git status --short` 核对。提交后执行：

```sh
git show --stat --oneline HEAD
git show --format= --check HEAD
git status --short --branch
```

现有校验器验证目录、主题 YAML、模板、来源 Schema、去重键与关联，不验证模型审阅可靠性、运行清单、费用或自动合并。后续实施需覆盖以上验收场景；本轮检查通过只代表设计保存一致、现有知识库规范有效，不代表定时或自动入库已实现。
