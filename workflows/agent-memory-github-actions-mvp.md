# Agent Memory 定时研究任务 MVP 设计

- 版本：0.1；设计日期：2026-10-18。
- 状态：**仅设计，尚未实现或启用**。本文中的频率、路径与参数是后续实施约定。
- 目标：由 GitHub Actions 定时发现 Agent Memory 新资料，核实原文并形成带证据的研究草稿，通过 PR 审阅后入库。
- 基础：沿用 [研究主题配置](../config/research_topics.yaml)、[Schema v1](source-schema.md)、[维护规范](maintenance.md)和现有论文、博客模板。保持 Markdown + YAML，不引入数据库或 Agent 框架。

## 1. 首版范围与成功标准

闭环为：**定时触发 → 发现与查重 → 获取原文 → AI 辅助研究 → 校验 → 草稿 PR → 人工审阅合并 → Obsidian 拉取**。

首版只处理启用的 `agent-memory`，产出新来源笔记、已有来源的更新建议、批次记录。`agent-rl` 继续停用。研究报告、洞察、公众号文章沿用现有按需流程，不纳入首个定时任务，也不连接公众号发布接口。

一次成功研究必须有可核实的原始来源、稳定身份、阅读覆盖范围、证据定位和校验通过的草稿。Actions 执行成功、PR 创建成功和人工合并分别记录；只有合并到 `main` 才算正式入库。没有合适的新资料也是合法结果，必须保留扫描范围与筛选原因。

## 2. 触发频率与运行上限

| 项目 | MVP 决策 |
| --- | --- |
| 主入口 | 每天北京时间 **08:17**；按 UTC 表达的拟用 cron 为 `17 0 * * *`。仅写在本文，不创建工作流配置。 |
| 执行环境 | GitHub 托管的 Ubuntu runner，从默认分支 `main` 读取已审阅的程序与配置；不依赖本地 Codex、ChatGPT Work 或 Obsidian 在线。 |
| 辅助入口 | 后续提供 `workflow_dispatch`，仅用于验收、恢复已有批次和指定日期区间补跑；所有入口共用查重、预算和写入规则。 |
| 初次扫描 | 最近 7 天，以原文首次发布或原文更新线索发现资料；既有 MemGPT、Memory Blocks 资料参与查重。 |
| 后续扫描 | 各来源从已合并的完整扫描游标向前重叠 48 小时，扫描到本批固定截止时间；缺失多天时分批追赶。 |
| 发现上限 | 每个来源每轮最多检查 50 条候选元数据，超额保留续扫信息，不能标记为已完整扫描。 |
| 深读上限 | 每批最多 3 份，优先 2 篇论文 + 1 篇博客；不足时可互补，同一博客发布方最多 1 篇。更新建议也占名额。 |
| 时间与模型 | 每次执行最多 30 分钟；每份资料最多 2 次模型请求尝试，整个批次累计最多 6 次。正常使用为 1 次研究 + 可选 1 次格式修复；网络重试、恢复重试也占名额，不能每次补跑重置。每次输入上限 16,000 token、输出上限 2,000 token；超限不得静默截断后声称阅读全文。 |
| 待审上限 | 最多 1 个未完成研究批次、1 个待审 PR。待审时后续定时运行只核对状态并提示积压，不新增付费研究；下次可运行时按游标追赶。 |

启用前必须确定支持上述限制的具体模型 ID、单批费用上限和月度费用上限，并以未来配置明确记录。额度耗尽或费用无法核算时停止模型调用，保存待办；缺少 API Key、模型或预算配置时直接失败，不自行选择替代模型或凭据。

GitHub 的定时执行可能延迟，繁忙时排队任务也可能被丢弃，因此 08:17 是计划时间，不是准点承诺；避开整点只是降低拥堵的选择。设计采用 UTC 表达，不依赖 runner 本地时区。参见 [GitHub schedule 文档](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)。

## 3. 资料来源与筛选

首版采用三个固定的一手来源，不做开放网页搜索或转载站抓取。关键词取自主题配置，筛选时同时判断是否涉及 Agent 的记忆机制；仅讨论 GPU 内存、缓存容量等内容不入选。

| 来源 | 发现方式与范围 | 原文及研究注意事项 |
| --- | --- | --- |
| arXiv | 使用[官方 API](https://export.arxiv.org/api/query)，组合 Agent 与记忆关键词，按 `lastUpdatedDate` 降序分页。初期重点关注 cs.AI、cs.CL、cs.MA；在实现验收中检查漏检与噪声。 | 阅读版本固定的官方 HTML 或 PDF 文本；保留基础 arXiv ID、实际读取的 `vN`、首次发表与更新时间。旧论文新版本也需发现，不能只按首次提交日期查询。 |
| Letta | 从[官方博客列表](https://www.letta.com/blog/)获取原文链接，筛选 memory、context management、Agent 长期状态等主题。 | 原文区分产品设计、工程经验与实验结论；不把产品宣称直接当成普遍有效的研究事实。 |
| LangChain | 从[官方博客列表](https://www.langchain.com/blog)获取原文链接，筛选 long-term memory、context engineering 等主题。 | 记录真实署名与原文日期，区分框架能力、实现建议和有证据的效果。 |

截至设计核对日，LangChain 的旧 `blog.langchain.com/rss/` 地址跳转后返回博客 HTML，不能作为已验证的 RSS 使用；Letta 首版也采用官方列表页，不假设存在可用 RSS。列表格式、内容类型或域名跳转不符合预期时报告来源异常，不能把解析失败当成零新增。

arXiv 的 `published` 表示首次版本日期，`updated` 表示当前版本更新时间；按更新排序后在本地检查扫描时间窗。API 分页遵守官方限速，连续请求至少间隔 3 秒，参见 [arXiv API 手册](https://info.arxiv.org/help/api/user-manual.html)。博客列表通常不能完整揭示旧文修订，因此每天额外轮查最多 5 个已入库博客 URL，按上次核查时间轮转；这不代表可以发现所有站点的所有历史更新。

候选先按主题相关性、是否提供新机制或评测证据、是否与现有研究形成补充排序。同分时优先较早积压项。未选中候选记录原因：无关、重复、待核实、额度延后或人工拒绝；额度延后项保留在批次待办中，不能因推进扫描游标而丢弃。不同公司博客增加了视角，但不构成行业趋势的充分证据。

## 4. 研究执行方式

采用轻量 Python 流程负责控制，模型只做有边界的阅读与分析。拟使用 [OpenAI Responses API](https://developers.openai.com/api/docs/guides/text) 调用单个模型；模型和费用需在启用前确认，不使用本地 Codex 登录态或订阅额度作为 runner 的认证方案。

1. **规划与身份预留**：扫描、规范化身份、核对全库及待审记录，生成批次清单。新来源先生成 UUID v4 并持久化，再调用模型，防止中断重试产生新身份。
2. **获取证据**：只访问白名单来源及经核实的原文链接。优先 HTML，其次可直接提取文本的 PDF；首版不增加 OCR、浏览器自动化或付费墙绕过。抓取受阻或文本不足时记录待处理。
3. **确定阅读范围**：明确标注 `full_text`、`excerpt` 或 `abstract_only`。原文超过输入限制时选择相关章节并标为节选；只有摘要时只能生成摘要级线索，不输出全文评测结论。
4. **模型分析**：输入原文证据包和研究问题，输出摘要、关键主张、证据 ID、局限、与 Agent Memory 的关系及可选推断。原文事实、作者主张、模型推断分别标识；没有证据时写“未核实”。
5. **确定性写入**：程序根据模板生成 Markdown。原始身份、日期、状态、路径与关联由规则及已核实元数据确定，不能由模型任意填写。未知作者为 `[]`、未知发布时间为 `null`。博客页面署名优先于泛化的机构结构化标签；冲突保留待审。
6. **校验与提交**：检查 Schema、引用、证据支持、身份冲突、写入路径、预算与人工内容保护；失败项不得伪装成正式资料。

证据包至少记录：原文 URL、抓取时间（UTC）、读取版本、规范化正文散列、覆盖范围、章节/页码/段落定位及支持主张的短摘录。笔记保留可点击的原文引用与对应定位；批次清单记录模型 ID、提示词版本和 token/费用用量。只保存必要短摘录与散列，不将整份 PDF、网页镜像或完整模型请求写入仓库。HTTP `Last-Modified` 和正文散列变化都只能作为更新线索，不能冒充作者确认的修订日期。

抓取内容视为待研究资料，其中的命令或提示不具备执行权限。模型不持有密钥，不访问 shell，不直接写仓库；只接收证据文本。API Key 仅由后续受信任的 API 调用步骤读取 GitHub Secret，不进入提示词、笔记、清单、日志或 PR。

## 5. 去重与更新

沿用[维护规范](maintenance.md)的全部身份键：arXiv 基础编号、规范化 DOI、保守规范化的 canonical URL；同一条资料的每个已知键都必须比较。查重范围包括 **`main` 全库、未完成批次/待审 PR、当前批次以及已记录的人工处理决定**。

| 情况 | 处理 |
| --- | --- |
| 新身份，原文和元数据足够 | 预留稳定 ID，生成一份 `status: inbox` 的新笔记，正文标注“AI 研究草稿，待人工核实”。 |
| 已有身份、同版本且正文无实质变化 | 跳过深读，记录核查结果；不刷新笔记日期或状态。 |
| 同一论文出现新版，或已知博客正文有变化 | 生成独立更新建议，引用原记录、新旧版本/散列和变化证据；不改已有来源文件。 |
| 多个身份键指向不同记录，或只有标题相似 | 标为身份冲突，交人工核查；不自动合并、不另建可能重复的来源。 |
| arXiv 预印本与期刊论文可能相同 | 只有原始元数据或原文明确证实对应关系才共用身份；否则待核实。 |
| 博客解读论文 | 两份来源保留各自身份；关联只引用已存在且核实的 ID，不修改旧记录的反向关联。 |

arXiv 的 `abs`、`pdf`、不同 `vN` 归为同一基础编号；博客 URL 按现行规范保留可能影响内容的查询参数、路径大小写等。自动化不得用“标题看起来一样”替代身份核实。

`published_at` 是首次发布时间，`collected_at` 是首次录入日期，`updated_at` 是本库笔记修改日期；原文更新时间另记于正文或批次清单，不改变这些字段含义。新版来源沿用原 ID，新证据不能触发整篇笔记重生成。

## 6. 写入边界与人工笔记保护

未来任务只允许以下输出；本轮不创建这些运行数据目录或文件：

| 路径 | 写入规则 |
| --- | --- |
| `sources/papers/<paper-id>.md`、`sources/blogs/<blog-id>.md` | 只创建已预留 ID 的新文件，严格使用现有 Frontmatter。已有文件不可覆盖，包含机器人先前创建但人工已修改的草稿。 |
| `reports/research-runs/<batch-id>/manifest.yaml` | 第一次模型调用前创建规划清单，记录时间窗、候选身份、预留 ID、基线 commit、来源游标和预算。规划完成后冻结；人工审阅修订须显式记录。 |
| 同批次下的 `attempt-<n>.yaml` | 追加新文件，记录本次执行、已完成项、失败项、待办、用量及结果文件散列；重试不覆盖旧执行记录。 |
| 同批次下的 `summary.md`、`updates/<existing-source-id>.md` | 创建一次，列出研究结果与独立更新建议；后续补跑的补充说明另建带 attempt 编号的文件。 |

`batch-id` 采用固定逻辑时间槽（如 `agent-memory-20261019T001700Z`），`attempt` 递增并关联 GitHub run ID。手动补跑沿用原批次 ID、截止时间、候选身份及已预留 UUID；额外历史区间采用单独批次并执行同样查重。

**所有已有正文、人工笔记、阅读状态、主题和关联均受保护**，包括旧资料与待审 PR 中人工编辑的内容。首版 AI 可以填充新笔记的研究草稿部分，人工笔记章节保持空白；生成草稿并不代表人工完成分析，不能自动设置 `analyzed`。自动化无权修改模板、Schema、主题配置、既有研究报告、洞察、文章或 `.obsidian/`。

以本批开始时的 `main` 和远端机器人分支 commit 为基线，在写入及推送前再次核对。发现已有文件变化、远端分支被人工提交、主分支新增同身份资料或路径冲突时保留现场并停止发布，等待审阅或重新校验。禁止强推、覆盖式恢复和自动解决笔记冲突；恢复时只有与上次机器散列一致的既有产物可复用，也无需重写。

## 7. 状态、失败补跑与游标

使用仓库中的 YAML 清单和 Git 分支保存状态，不依赖 runner 磁盘、缓存或短期 artifact 作为唯一记录。

- **批次**：`planned → researching → review_pending → merged`；另有 `partial`、`failed`、`waiting_decision`。批次完成、资料完成、来源扫描完整性分别记录。
- **资料**：`discovered → queued → researched → validated → proposed → accepted/rejected`；失败保存阶段、原因和可重试性。这里是运行状态，不是来源 Frontmatter 的 `status`。
- **来源游标**：只有完整扫描区间及其待办清单经 PR 合并后才生效；失败来源、未扫完分页不能推进。成功来源可独立推进，不因其他来源故障丢失结果。

首个模型调用前，将规划清单提交到 `codex/agent-memory-<时间槽>` 分支。分支创建/保存失败则不开始付费研究；后续执行优先恢复未完成批次。每完成一份资料，保存结果与新的 attempt 记录到同一分支，减少中断后重复调用。模型完成与结果持久化之间的崩溃窗口仍可能导致一次重复付费调用，应在用量中标明，不宣称执行“恰好一次”。

每个研究 job 开始前，由独立写入 job 将获准的模型调用槽位与最大费用预留持久化到远端执行记录；按每份资料的小批次分配，所有 attempt 合计受同一批次和月度额度约束。关闭 SDK 隐式重试，由流程统一计数。超时或崩溃后无法确定是否计费的请求按预留上限消耗处理，不能自动返还；只有能确认未发送的预留才可释放。恢复前重新核算余量，不能通过新建批次绕过月度预算。

待审期间不自动改写 PR。部分结果合并后，失败项与额度延后项转入下一批清单，沿用已预留的来源 ID，并引用原批次；原批回执保留。恢复时若原文散列改变，记录新证据版本并重新核查，不能混用新旧证据或无条件复用旧分析。

| 失败或异常 | 补跑策略 |
| --- | --- |
| 网络超时、429、5xx | 抓取请求最多重试 2 次，指数退避并遵守 `Retry-After`。模型请求仅在剩余调用槽位与预算允许时重试，仍受每份 2 次、每批 6 次的总上限约束；未知计费保守计入。仍失败则记录后继续其他候选。403、认证失败不反复重试。 |
| 列表解析异常、分页未扫完 | 标记该来源 `partial/failed`，保存续扫线索，不推进其完整扫描游标。恢复时重新重叠扫描并去重，不能信任变化列表的固定页码等于稳定快照。 |
| 原文不可读、证据不足或模型输出不合格 | 最多一次格式修复；实质证据不足保留待核实，不用更多调用猜测补全。修复也计入总调用与费用上限。 |
| 部分资料失败 | 已验证结果可进入标有 `partial` 的草稿 PR；失败项和额度延后项保留在清单。仅重试未完成项，复用已保存结果。 |
| 运行超时或取消 | 下次定时或手动恢复同一批次，读取远端规划和 attempt 记录；已预留 ID 不变。 |
| 连续多天没运行、队列任务丢失 | 从最后已合并游标补扫描；达到上限就分批继续，不能直接把游标跳到当天。 |
| 待审 PR 未处理 | 定时运行报告等待审阅，不继续产生研究 PR 或消费模型额度；不推进游标。 |
| PR 被关闭但未合并 | 进入 `waiting_decision`，保留分支和待办，不视为入库或自动重新提交。人工选择重开，或通过仅含处理清单的 PR 合并拒绝/跳过决定；拒绝项保留身份与理由。 |

无新资料且扫描完整时，可生成仅含扫描回执和游标的 PR，便于持久化“确实检查过”；同一时间窗已有回执就不重复创建。全来源失败时保留分支执行记录并让 Actions 明确失败，不创建“研究成功”PR。达到筛选配额但扫描尚未完成时，完整游标保持原值，待办与继续位置单独保存。

定时、补跑和发布采用同一个 concurrency 组，`cancel-in-progress: false`。GitHub 的待运行队列不能替代持久待办，补跑完整性依靠游标与清单，参见 [GitHub concurrency 文档](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)。Actions Summary 展示每个来源上次完整扫描、最近成功研究、待审批次和错误；异常通过 GitHub 自带运行状态及 PR 呈现，首版不增加外部消息渠道。

## 8. 提交、权限与审阅流程

1. 定时任务读取 `main`，确认无其他未完成批次后创建机器人分支并保存规划。只处理受信任的默认分支代码；来自 fork 或研究资料中的内容不能开启带密钥的任务。
2. **权限按独立 job 隔离**：研究 job 只有 `contents: read`，需要调用模型时才注入模型 Secret；保存规划、预留额度及发布 job 获得必要的 `contents: write`，不注入模型 Secret；创建草稿 PR 的 job 另需 `pull-requests: write`。GitHub token 的权限不能靠同一 job 内不同 step 隔离，参见[官方权限说明](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token#modifying-the-permissions-for-the-github_token)。程序用路径白名单约束写入，不能误以为 token 本身具有路径级权限。
3. 校验拟提交的确切内容后，普通提交推送到机器人分支，创建 **Draft PR**，目标为 `main`。不直接推送主分支，不自动合并；标题注明批次、来源数量和是否部分失败。
4. PR 正文列出扫描区间、来源覆盖、查重结果、新增/更新建议、事实与推断、阅读限制、用量、失败待办以及校验结果，并链接批次清单。
5. 人工核对原文、证据、身份、笔记差异和更新建议。接受的新资料经修改后合并；已有资料的更新建议由人工按段落应用，继续遵守维护规范。拒绝资料移出来源目录，同时在处理清单保留拒绝决定。
6. 合并前再次对齐最新 `main` 并校验；基线变化必须重新核对身份与文件散列，不能靠旧绿色检查认定新内容安全。人工确认后合并，清单才成为正式游标及去重决定；Obsidian 按现有 Git 同步拉取 `main`。

GitHub token 采用最小权限，并检查仓库允许 Actions 创建 PR。权限不足时明确失败，不自动启用仓库设置或退回个人 token。由于 `GITHUB_TOKEN` 触发后续工作流有专门规则，研究任务自身必须完成校验，不能假设机器人提交一定触发全部 PR 检查。当前官方文档也说明部分机器人 PR 事件会创建待批准的工作流运行，参见 [GITHUB_TOKEN 说明](https://docs.github.com/en/actions/concepts/security/github_token)。

本地审阅前先同步，避免 Obsidian 的自动提交与云端更新并行造成冲突。发生冲突时保留两侧内容并人工解决；当前 Obsidian 配置不在本任务修改范围。草稿 PR 里的资料未合并前不会进入本地主分支知识库。

## 9. 后续实施内容与启用门槛

本文确认设计后，下一步才是实现一个**尚无 schedule 的**最小工作流及其验收。预期新增 `config/research_sources.yaml`、`config/research_task.yaml`、轻量执行脚本和 `.github/workflows/agent-memory-research.yml`；具体拆分以实现审阅为准，不在本轮创建。

启用前依次完成：

1. 实现发现、证据提取、查重、清单恢复、白名单写入和草稿 PR；固定依赖/Action 版本并检查权限。先用本地固定样例进行无网络、无模型费用的演练。
2. 确定模型、单批/月度费用上限、来源配置和 GitHub Secret；检查令牌权限与密钥隔离。当前设计不读取或添加密钥。
3. 增加运行清单与保护规则校验，验证下表场景。经授权再进行一次有严格额度的真实手动验收，检查草稿 PR 和中断恢复。
4. 人工接受验收结果后，通过单独审阅的变更添加 schedule，才开始每天执行。当前设计文档的提交与合并不等于授权启用定时任务。

| 验收场景 | 必须观察到的结果 |
| --- | --- |
| 正常新增论文、博客 | 原文可核实，草稿引用可定位，严格符合 Schema，状态为 `inbox`。 |
| 同批、隔日、待审 PR 中发现同一来源 | 不重复建档或分配新身份；明确记录跳过原因。 |
| arXiv abs/pdf/vN 与已入库论文 | 识别为同一研究；新版只产出更新建议，旧文件散列不变。 |
| 标题相似、DOI/arXiv 键冲突 | 停止自动身份合并并提示核查。 |
| 只有摘要、正文截断或证据不支持结论 | 明示覆盖不足，降级为线索或阻止发布相应结论；不能假装全文分析。 |
| 人工修改既有笔记或待审分支 | 原文逐字保全，任务停止覆盖；人工状态及关联不变。 |
| 缺少密钥/预算、费用耗尽 | 无越限模型调用，无新凭据回退，保存明确错误或待办。 |
| 单来源 403/解析失败，其他来源成功 | 区分部分成功和零结果；失败来源游标不前进。 |
| ID 预留后中断，或保存结果后 PR 创建失败 | 补跑沿用 ID 与已存结果，只继续未完成阶段，无重复 PR。 |
| 延迟触发、漏跑、扫描超过配额 | 时间窗固定、重叠查重、分批追赶，无游标跨越未覆盖区间。 |
| PR 关闭、拒绝或主分支出现同身份资料 | 没有假成功或自动覆盖，处理决定和冲突可追溯。 |
| 当前设计提交 | 只有本文与工作流索引变化，没有可执行定时任务或公众号发布。 |

## 10. 当前设计的可复现检查

在仓库根目录执行（现有校验器依赖见 `workflows/requirements.txt`）：

```sh
python3 workflows/validate.py
git diff --check
git diff -- workflows/README.md workflows/agent-memory-github-actions-mvp.md
git status --short
git ls-files '.github/workflows/*'
```

最后一项用于核对是否意外新增实际工作流；本轮预期没有输出。未跟踪文件同时通过 `git status --short` 检查。提交后可用以下命令核对提交范围及格式：

```sh
git show --stat --oneline HEAD
git show --format= --check HEAD
git status --short --branch
```

现有校验器验证目录、主题 YAML、模板、来源 Schema、去重键和关联，不验证本方案中的运行状态机、证据正确性、费用或定时执行行为。上述场景需在后续实现阶段补充针对性验证；本轮通过检查只代表设计已保存、仓库资料规范仍然成立。
