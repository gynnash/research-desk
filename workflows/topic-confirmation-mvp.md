# 真实选题确认入口 MVP

2026-10-19 已实现真实本地确认页、正式选题证据校验、冻结预览、确认与撤回记录，以及 Git 保存和同步重试。2026-10-20 已接通[真实会员 Writing](writing-agent-member.md)：只处理用户在页面确认并同步的选题，三阶段独立审阅，输出仍只在 test，不发布公众号。 自动 Research → Insight → 独立审阅 → 正式入库继续按既有配置运行。入口沿用 Markdown、YAML、Git 和当前本地/远程主机，不建设线上平台或数据库。

## 首版交互

**默认入口是本地浏览器确认页：先展示完整预览，再由用户直接点击确认。** 页面仅监听本机环回地址，使用 Python 标准库 HTTP 服务和原生 HTML/CSS/JavaScript，无前端框架、CDN 或外部页面依赖。服务启动后打开 [选题工作台](http://127.0.0.1:8765)，日常直接在浏览器操作；也可以请 Codex 帮助打开页面。Obsidian 继续用于阅读选题卡和证据，修改卡片状态、打勾或添加“同意”都不直接授权写作。

未来若宿主能向确认程序提供可验证、直接来自用户的消息事件，再增加自然语言确认适配。模型转述“用户已同意”、模型输出 `confirmed`、静默、研究任务的既有授权，均不能替代这个事件。未完成宿主来源验证前，不把聊天里的模型回复当成确认入口。

当前页面流程：

1. 待确认列表只显示已正式准入、仍为 `proposed` 的卡片，显示标题、方向、生成日期及证据范围。
2. 用户打开一张卡，查看标题、写作角度、受众、目标字数、证据与缺口、三阶段范围、生成/审阅模型、调用上限及“不会发布公众号”。调整角度、受众或字数后刷新冻结预览包，不修改原选题卡。
3. 用户查看最终预览，自行勾选范围说明，再点击“保存写作确认”。不预选同意、不提供默认或批量批准；模型与 CI 不得代点。修改标题或角度不代表新增观点已被模型核实，确认范围仍受已有证据约束。
4. 服务追加确认事件并普通提交推送。同步成功后可在“确认记录”单独点击“开始 / 继续测试写作”，派发 GitHub Writing 作业；确认本身不调用模型。可查看阶段、调用数和只读测试稿，也可撤回或重试同步。正式文章准入仍未启用。

当前可预览的是[正式选题卡](../articles/agent-memory/cycle-agent-memory-gh-20261019-topic-1.md)。本轮未代为确认：其中 R1 只阅读论文摘要，R2 只阅读博客节选，历史 H1 保留历史基线身份。页面展示这些缺口，可打开只读笔记；选择这个题目不会自动补全文或宣称已核实评测结果。没有合格正式选题时显示空状态；读取、证据失效或同步失败时显示实际错误，不用虚构卡片填充。

## 确认绑定与准入检查

预览包是给用户审阅的冻结输入，确认绑定以下内容，不只绑定易变的标题或 ID。真实授权由页面采集用户操作，不由模型创建：

| 绑定 | 必需内容 |
| --- | --- |
| 仓库与选题 | 工作台稳定 ID、方向、选题 ID、规范相对路径、当前文件 SHA-256、基线 commit。 |
| 用户选择 | 最终标题、角度、受众、目标字数，以及这些字段的规范序列化散列；若调整观点超出证据范围，先补证据或返回 Insight，不直接写作。 |
| 证据与审阅 | 精确的来源、Research 报告、洞察及历史基线路径/散列；来源规范 URL、版本、阅读范围；独立审阅回执、准入计划、`accepted` 回执及其 SHA-256。 |
| 执行范围 | 大纲、初稿、候选稿三个阶段；确认配置及其散列、未来写作的生成和审阅 model ID、批次/阶段请求上限、最多一次修订；`writing_started: false`、`publish_authorized: false`。 |
| 确认来源 | 预览 ID 与散列、确认 ID、UTC 时间、`origin: local_confirmation_page`、明确操作及本地会话事件 ID；不保存聊天全文、主机绝对路径或秘密。 |

只接受在 `main` 上可追溯的正式选题：必须核对独立生成/审阅 model ID 不同、审阅 `pass` 绑定当前候选与输入、准入回执 `production_accepted: true`、选题属于准入输出。不能因为卡片正文写了“通过审阅”或存在 `accepted.yaml` 文件就放行。

读取正式来源时使用准入模块验证后的有效输出散列：已有[机械链接修复记录](formal-admission.md)须连同原始计划和回执一起验证，不能绕过历史记录直接信任新文件。人工历史资料作为 `human_baseline` 绑定当前文件散列，不伪造模型通过记录。

当前在生成预览、确认前及读取确认状态时重新检查这些绑定。相关输入、角度、受众、配置或审阅变化后，旧预览拒绝确认，已有确认显示失效，需要重新预览；`main` 新增无关文件不使确认失效。手工改动证据后不能沿用旧确认。真实 Writing 已在每次模型请求与产物创建前 fetch 远端并复核绑定和撤回，使用确认 ID 绑定唯一稳定测试批次；不改写原确认，不增加正式 claim 文件。

## 人类授权与不可变记录

模型生成/审阅进程只接收冻结证据包，不提供确认工具、确认目录写入能力或页面控制。手写 YAML、`origin: human` 标签和文件 SHA 都不能证明人类操作。首版由用户控制的受信任本机确认进程采集明确点击，写出事件；不引入账号平台、私钥或公钥管理。Git 和本机写权限是信任前提，不能抵御有相同本机权限的恶意代码，不能宣称 SHA 证明真人。

页面服务提供列出、只读证据与已核验测试稿、预览、确认、撤回、同步重试，以及派发 GitHub Writing 作业；不持有会员令牌、不直接调用模型、不连接公众号。只绑定 `127.0.0.1`；校验 `Host`、同源 `Origin` 和每次启动随机会话 CSRF token，状态变更只允许 `POST`。每个冻结预览默认 15 分钟有效，有一次性 nonce；确认时核对当前散列并原子消费，双击、过期预览和跨站请求不能创建第二个确认。页面刷新后需重新预览，服务重启后原 nonce 和会话 token 全部失效。确认和撤回均展示明确结果，不把页面打开或请求 `GET` 当作批准。

实际记录位于 `reports/<topic>/writing-approvals/<approval-id>/`：确认时新建 `preview.yaml`、`confirmed.yaml`，撤回时追加 `revocations/<event-id>/event.yaml`，各自配对 SHA-256。每组文件先在仓库外的同文件系统临时目录完整写入，再原子安装整个目录，避免留下半份确认。撤回关联原确认 ID，不改写原确认或选题卡。状态由有效事件和当前输入校验推导，不反复修改 `approved: true`。仅查看或生成预览不落盘，nonce 和 CSRF token 只保存在进程内存，不提交仓库。当前写作占用由稳定批次 manifest、请求事件及共用 GitHub 并发组实现，没有单独的 `invalidations/` 或正式 `claims/` 文件。

当前每次真实确认拥有稳定的确认 ID，已有效确认的题目不会再次出现在待确认列表。真实 Writing 使用 `writing-<approval-id>` 稳定批次；重复启动只恢复原批次，不生成第二篇文章或刷新预算。撤回在本机或最新 fetch 的远端出现后，阻止后续请求或产物写入；已发出的请求可能仍消耗用量。已有记录和稿件保留，撤回不授予发布权限。

## Writing、预算与恢复

沿用[离线 Writing](writing-agent-offline.md)的顺序和证据规则：大纲 → 初稿 → 发布候选稿，每阶段先做确定性校验，再由不同模型、独立上下文审阅；通过才继续。区分原文事实、作者主张、我们的推断及通俗比喻，保留原文与报告引用，不将摘要、节选升级为全文核查。每阶段最多修订一次，仍不通过即停止。

正常三个阶段为 6 次调用，含修订复审最多 12 次；使用 YAML 中更严格的实际批次/阶段限制，并与 Research、Insight 共用[会员请求预算](membership-budget.md)，不另开账本逃避每月上限。会员凭据仍在既有仓库外 profile；GitHub 发布步骤不读取它。执行预算不足时先停止，不因人工确认而突破限制。

首个真实会员验收仅新建 `articles/test/<topic>/<batch-id>/{outline,draft,candidate}.md`，回执与请求事件放 `reports/test/<topic>/writing-runs/<batch-id>/`。真实确认记录使用独立的真实授权目录，不能由 `confirm-fixture`、`origin: offline_fixture` 或 mock 回执升级而来；生产输入也不能读取测试稿为正式证据。真实会员调用与模拟次数分别记录。

恢复沿用原确认、批次、冻结输入、请求预留和检查点；通过阶段直接复用，未知请求不盲目重发。完成的缓存重放不增加调用。已有稿件若被人工编辑则停止，保留两份内容；不覆盖旧稿、不重新生成后替换。正式文章准入后沿用 create-only，每阶段另存新文件，候选稿始终没有公众号发布授权。

## Git 同步、部署与配置

当前 Mac 提供本地页面，既有 Git 同步方式保持不变。确认器使用与执行器分离的干净工作目录，位于仓库和 Obsidian Vault 外；启动及生成预览前核对并同步 `main`，记录所用 Git 基线，在单工作台锁下创建新记录并普通提交推送，不在 Vault 中自动暂存用户改动。存在同名冲突、输入变化或非快进推送时停止并保留确认现场，不强推或自动解决人工笔记冲突。Obsidian 仍通过已有 Git 同步看到记录。

确认已保存在本机但推送失败时，页面显示 `pending_sync`（确认待同步）或 `revocation_pending_sync`（撤回待同步），提供“重试同步”继续同步同一记录。重试不会再次批准题目或追加一份确认。遇到冲突、非确认文件改动或同步状态不明时，先保留现场并处理网络/冲突；不要重复确认、重置目录或强推。只有记录到达共享 `main` 且再次校验后，未来执行器才允许使用；当前所有状态均不会派发 Writing。

后续 Writing 使用现有唯一会员执行通道与 Research 共用串行队列；不能一边在 Vault 调用会员、一边让 runner 并行运行。确认器当前只保存确认，不创建写作任务；未来执行器须在独立工作目录复核最新确认、撤回和输入，请求记录与研究共享预算。远程部署也仅监听该主机环回地址，用户通过自己的安全连接/端口转发打开页面，不直接暴露公网；每个用户在执行主机自行完成官方会员授权。首版不做多主机账户协调。

[`config/confirmation.yaml`](../config/confirmation.yaml) 提供工作台 ID、方向、环回端口、预览有效期、未来写作模型、预算及字数范围。当前默认约 2,000 字，允许 800–5,000 字；写作最多 12 次、每阶段最多 4 次及一次修订，仅为冻结授权范围，尚不会消耗会员用量。`workspace: null` 自动选择主机本地 Vault 外目录，开源用户可自行配置本地或远程主机路径；共享配置不保存个人路径、OAuth 或会话 token。允许目录、用户确认及不发布的边界不能由配置放宽。

## 实现顺序与少量验收

1. **已实现只读预览和绑定**：读取真实正式卡，校验准入及有效散列，展示证据缺口、角度/受众和预算；仅预览不创建确认或调用模型。输入变化时旧预览不可确认。
2. **已实现用户确认和撤回**：环回页面、同源/CSRF/nonce、追加记录及 Git 保存；有过期、重复确认、撤回、输入变化及同步失败保护。隔离样例承担确认操作验收；本轮不替用户确认真实题目。执行占用仍属于下一阶段。
3. **小额度会员 Writing**：用户实际确认一张卡后，再接入既有会员主机；默认只写 `test`，验收一次大纲/初稿/候选稿及一次缓存恢复，核对真实账本，不重复做大规模测试。
4. **正式文章准入**：测试通过后单独启用 create-only，确认、证据、独立审阅和 Git 回存均可追溯。自然语言直接确认适配、GitHub 手动入口和托管网页平台按需求后置；公众号发布仍是单独授权的未来能力。

本轮交付页面与保存入口，不代为创建真实确认、写作任务或新调度。用户可自行打开页面决定是否确认；真实会员 Writing 和公众号发布仍未接通。

## 维护附录

日常只需在浏览器操作。以下供首次部署或维护使用，在仓库根目录执行；需要已有的 Python/PyYAML 环境、`main` 上已提交的页面与配置，以及可访问该仓库的既有 Git 凭据。页面不读取会员授权文件。

```sh
# 首次准备 Vault 外的独立确认工作目录；不会创建确认或调用模型
python3 scripts/researchdesk_confirmation.py setup

# 本机启动并打开浏览器；终端需保持运行，停止后可再次启动
python3 scripts/researchdesk_confirmation.py serve --open-browser
```

默认地址是 `http://127.0.0.1:8765`；端口可通过配置或 `serve --port 8766` 调整。Mac 默认工作目录为 `~/Library/Application Support/ResearchDesk/confirmation-workspace`，其他系统默认 `~/.local/share/ResearchDesk/confirmation-workspace`。准备步骤会复用匹配当前远端的工作目录，拒绝将其他已有目录覆盖为工作台；页面不自动常驻或新建定时任务。远程主机使用自己的环回地址并由用户配置安全端口转发。

服务重启会使尚未确认的预览过期；刷新页面后重新核对即可，已保存记录保持不变。确认请求失败或结果不明时，先进入“确认记录”刷新核对；待同步使用“重试同步”，不要通过重新确认规避错误。确认工作目录存在人工改动或两侧并发提交时，服务保留两侧文件并停止自动合并，需维护者处理后重新启动或重试。
